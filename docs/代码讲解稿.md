## 二、实体层（Entity）— 数据模型

### 2.1 User.java — 用户实体

**文件路径**: `src/main/java/com/secondhand/mall/entity/User.java`

**处理内容**: 用户账户信息，包括登录凭证、个人资料、余额、会话管理。

**核心字段**:
| 字段 | 类型 | 说明 |
|------|------|------|
| username | String | 唯一登录名 |
| password | String | BCrypt加密存储 |
| role | String | "user" 或 "admin" |
| balance | BigDecimal | 账户余额，默认10000元（模拟充值）|
| sessionId | String | 当前会话ID，用于单点登录控制 |
| avatar | String | 头像路径，默认 "/user-avatar/default.jpg" |

**运用技术**:
- `@Entity` + `@Table` — JPA实体映射
- `@PrePersist` — 自动填充创建时间、默认角色、默认余额
- `BigDecimal` — 金额精确计算，避免浮点误差

**实现逻辑**: 每个用户注册后自动获得10000元余额，用于平台内交易。`sessionId` 字段配合 `SessionValidationFilter` 实现单点登录——同一账号只能在一个地方登录。

---

### 2.2 Product.java — 商品实体

**文件路径**: `src/main/java/com/secondhand/mall/entity/Product.java`

**处理内容**: 二手商品信息，包括定价、成色、卖家信息、多图支持。

**核心字段**:
| 字段 | 类型 | 说明 |
|------|------|------|
| name | String | 商品名称（搜索关键词匹配字段）|
| category | String | 分类：手机、笔记本电脑、耳机等 |
| originalPrice | BigDecimal | 原价 |
| secondHandPrice | BigDecimal | 二手价（交易价格）|
| itemCondition | String | 成色：全新/几乎全新/轻微使用等 |
| imageUrl | String | 多张图片，逗号分隔存储 |
| quantity | Integer | 库存数量 |
| status | String | "active"/"sold"/"deleted" |
| sellerUsername | String | 卖家用户名（关联User表）|

**运用技术**:
- `@Column(columnDefinition = "TEXT")` — 大文本字段（描述、图片URL列表）
- 辅助方法 `getImageUrls()` / `setImageUrls()` — 逗号分隔字符串与List互转

**实现逻辑**: 商品图片采用"逗号拼接存储"方案——多张图片URL用逗号连接存为一个TEXT字段，读取时split成List。这种设计避免了额外的图片关联表，适合中小型项目。

---

### 2.3 Order.java — 订单实体

**文件路径**: `src/main/java/com/secondhand/mall/entity/Order.java`

**处理内容**: 交易订单，记录买卖双方、商品快照、收货信息、物流状态。

**核心字段**:
| 字段 | 类型 | 说明 |
|------|------|------|
| orderNumber | String | 6位随机订单号（唯一）|
| username | String | 买家用户名 |
| sellerUsername | String | 卖家用户名 |
| productName | String | 商品名称快照 |
| productPrice | BigDecimal | 下单时价格快照 |
| status | String | "unshipped"→"shipped"→"received"→"completed" |
| trackingNumber | String | 物流单号 |

**实现逻辑**: 订单采用"数据快照"模式——下单时把商品名称、价格、图片复制到订单表。这样即使商品被删除或修改，订单历史记录仍然完整。订单状态机严格约束流转顺序，防止跳步。

### 2.4 ChatRoom.java — 聊天室实体

**文件路径**: `src/main/java/com/secondhand/mall/entity/ChatRoom.java`

**处理内容**: 买卖双方针对某个商品的私聊房间。

**核心字段**:
| 字段 | 类型 | 说明 |
|------|------|------|
| user1Username / user2Username | String | 聊天双方 |
| productId | Long | 关联商品 |
| lastMessage | String | 最后一条消息预览 |
| user1Unread / user2Unread | Integer | 各自未读消息数 |

**实现逻辑**: 采用软删除（`deleted=true`）而非物理删除，保留聊天记录。未读消息计数器避免每次查询都要统计未读数。

## 三、配置层（Config）— 基础设施

### 3.1 SecurityConfig.java — 安全配置

**文件路径**: `src/main/java/com/secondhand/mall/config/SecurityConfig.java`

**处理内容**: Spring Security 安全策略配置。

**核心配置**:
```java
.csrf(csrf -> csrf.disable())  // 禁用CSRF（前后端分离，用Session认证）
.formLogin(form -> form.disable())  // 禁用表单登录（自定义登录逻辑）
.anyRequest().permitAll()  // 所有请求放行（权限由Controller手动校验）
```

**运用技术**:
- `BCryptPasswordEncoder` — 密码加密（单向哈希，不可逆）
- `SecurityFilterChain` — Spring Security 6.x 新写法（替代WebSecurityConfigurerAdapter）

**实现逻辑**: 这个项目"借用"了Spring Security的BCrypt密码加密能力，但禁用了它的认证链。所有认证逻辑都在Controller中通过Session手动实现。这样做的好处是简单直接，坏处是放弃了Spring Security丰富的认证功能。

---

### 3.2 SessionValidationFilter.java — 单点登录过滤器

**文件路径**: `src/main/java/com/secondhand/mall/config/SessionValidationFilter.java`

**处理内容**: 每次请求验证Session是否有效，实现单点登录（同一账号只能在一个浏览器登录）。

**实现逻辑**:
1. 放行静态资源（/css/、/js/、图片等）
2. 未登录用户访问需认证API → 返回401
3. 已登录用户：比对当前SessionID与数据库存储的SessionID
   - 不匹配 → 说明在其他地方登录了 → 踢出当前会话
   - 匹配 → 更新最后活跃时间，放行

**运用技术**:
- `javax.servlet.Filter` — Servlet过滤器
- `@Order(1)` — 最高优先级执行
- `userService.validateSession()` — 数据库级Session校验

**这是本项目的核心安全机制之一**。传统Session只存在浏览器Cookie中，无法感知"在别处登录"。这个过滤器把SessionID存到数据库，每次请求都校验，实现了真正的单点登录。

---

### 3.3 DataInitializer.java — 数据初始化

**文件路径**: `src/main/java/com/secondhand/mall/config/DataInitializer.java`

**处理内容**: 应用启动时确保管理员账号存在。

**实现逻辑**:
- `CommandLineRunner` — Spring Boot启动完成后自动执行
- 检查admin账号是否存在，不存在则创建（admin/admin123）
- 修复非BCrypt加密的旧密码（兼容性处理）

## 四、仓库层（Repository）— 数据访问

### 4.1 ProductRepository.java — 商品数据访问

**文件路径**: `src/main/java/com/secondhand/mall/repository/ProductRepository.java`

**处理内容**: 商品表的CRUD操作和复杂查询。

**核心查询方法**:
| 方法 | 功能 | 技术 |
|------|------|------|
| `findByIdForUpdate()` | 悲观锁查询 | `@Lock(PESSIMISTIC_WRITE)` |
| `searchActiveByKeyword()` | 关键词搜索 | `LIKE %:keyword%` 模糊匹配 |
| `findByCategoryAndPriceRange()` | 多条件筛选 | JPQL动态查询 |
| `findAllActiveOrderByNewest()` | 按时间排序 | JPQL + ORDER BY |

**运用技术**:
- `@Query` — 自定义JPQL查询
- `@Lock(LockModeType.PESSIMISTIC_WRITE)` — 悲观锁，防止并发超卖

**实现逻辑**: 搜索功能支持按商品名称和描述模糊匹配，同时支持分类、价格区间、成色的组合筛选。悲观锁用于订单创建时锁定商品记录，防止两个用户同时购买同一件商品。

## 五、服务层（Service）— 业务逻辑

### 5.1 OrderService.java — 订单服务（最核心）

**文件路径**: `src/main/java/com/secondhand/mall/service/OrderService.java`

**处理内容**: 订单创建、状态流转、取消退款、并发控制。

**订单状态机**:
```
unshipped（待发货）→ shipped（已发货）→ received（已收货）→ completed（已完成）
unshipped → cancelled（已取消，触发退款）
```

**createOrder() 核心流程**:
1. `productRepository.findByIdForUpdate(productId)` — 悲观锁锁定商品
2. 校验：商品是否存在、是否已售出、库存是否充足、是否买自己的商品
3. `userRepository.findByUsernameForUpdate(buyerUsername)` — 悲观锁锁定买家
4. 校验：余额是否充足、价格是否一致
5. 扣减买家余额
6. 递减库存（库存为0时标记sold）
7. 增加卖家余额
8. 创建订单记录

**运用技术**:
- `@Transactional` — 事务保证，以上步骤要么全部成功，要么全部回滚
- `@Lock(PESSIMISTIC_WRITE)` — 悲观锁，数据库行级锁
- `BigDecimal` — 金额精确计算

**这是整个项目技术含量最高的地方**。悲观锁+事务保证了并发场景下的数据一致性——两个人同时抢同一件商品，只有一个能成功。

---

### 5.2 ProductService.java — 商品服务

**文件路径**: `src/main/java/com/secondhand/mall/service/ProductService.java`

**处理内容**: 商品CRUD、搜索、筛选、分页。

**关键设计**:
- `fillSellerAvatar()` — 每次读取商品时，从User表获取最新头像覆盖到Product的sellerAvatar字段
- `searchProducts(keyword, category, minPrice, maxPrice, condition, sortBy)` — 多条件组合搜索

**实现逻辑**: 商品表的 `sellerAvatar` 是冗余字段（商品创建时复制的）。为了保证头像修改后所有商品都显示新头像，每次查询商品时都从User表重新获取——这是"读时更新"策略，用读性能换写简化。

---

### 5.3 UserService.java — 用户服务

**文件路径**: `src/main/java/com/secondhand/mall/service/UserService.java`

**处理内容**: 注册、登录、Session管理、头像上传。

**登录流程**:
1. 按用户名查找用户
2. `passwordEncoder.matches(rawPassword, hashedPassword)` — BCrypt验证密码
3. 更新 `sessionId` 到数据库（配合单点登录过滤器）
4. 返回用户信息

**运用技术**: BCrypt密码加密 — 每次加密结果不同（加盐），但验证时能正确匹配。

---

### 5.4 ChatService.java — 聊天服务

**文件路径**: `src/main/java/com/secondhand/mall/service/ChatService.java`

**处理内容**: 聊天室创建/查询、消息发送/接收、未读计数、软删除。

**关键设计**:
- 聊天室查找是双向的：`WHERE (user1 = A AND user2 = B) OR (user1 = B AND user2 = A)`
- 发送消息时自增对方的未读计数器
- 查询聊天室列表时批量解析对方头像，避免N+1查询

## 七、关键技术总结

| 技术点 | 实现方式 | 解决什么问题 |
|--------|----------|--------------|
| 密码安全 | BCrypt单向哈希 | 即使数据库泄露，密码也不可逆 |
| 单点登录 | SessionID存数据库 + 过滤器校验 | 同一账号只能在一个浏览器登录 |
| 并发控制 | 悲观锁(@Lock) + 事务(@Transactional) | 防止超卖、余额重复扣减 |
| 数据一致性 | @Transactional原子操作 | 订单创建的多步操作要么全成功要么全回滚 |
| 搜索功能 | JPQL LIKE模糊匹配 + 多条件组合 | 商品名称/描述关键词搜索 |
| 图片存储 | 本地文件系统 + UUID命名 | 上传图片保存到product-images/目录 |
| 订单快照 | 下单时复制商品信息到订单表 | 商品删除后订单记录仍完整 |
| 软删除 | deleted字段标记 | 聊天记录保留但不显示 |

## 八、数据流示例（用户下单）

```
1. 前端 POST /api/orders {productId, receiverName, ...}
   ↓
2. ApiController.createOrder() 获取Session中的username
   ↓
3. OrderService.createOrder() 开启事务
   ↓
4. ProductRepository.findByIdForUpdate() → 悲观锁锁定商品行
   ↓
5. 校验：商品状态、库存、是否自买
   ↓
6. UserRepository.findByUsernameForUpdate() → 悲观锁锁定买家行
   ↓
7. 校验：余额是否充足
   ↓
8. buyer.balance -= price → 保存买家
   ↓
9. product.quantity-- → 如果quantity=0则status="sold" → 保存商品
   ↓
10. seller.balance += price → 保存卖家
   ↓
11. 创建Order记录 → 保存订单
   ↓
12. 事务提交（以上步骤全部成功）
   ↓
13. 返回 {"success": true, "orderId": 123}
```
